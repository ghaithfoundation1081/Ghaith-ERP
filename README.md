# نظام غيث المتكامل (المشتريات · المخازن · الحسابات · التبرعات · الإدارة)

## الملفات
| الملف | مكانه |
|---|---|
| `Code.gs` + `Procurement.gs` + `Inventory.gs` + `Accounting.gs` + `Donations.gs` | خمسة ملفات داخل مشروع Apps Script نفسه (الترتيب غير مهم) |
| `index.html` + `mod-procurement.js` + `mod-inventory.js` + `mod-accounting.js` + `mod-donations.js` + `export.js` + `config.js` | على GitHub Pages في نفس المجلد |

## الترقية من النسخة السابقة
1. الصق ملفات `.gs` الخمسة (Code, Procurement, Inventory, Accounting, Donations) في Apps Script (استبدل Code.gs القديم)، ثم شغّل `setup()` مرة واحدة (تضيف الشيتات والأعمدة الجديدة دون مسح بياناتك).
2. انشر نسخة جديدة من الـ Web App (Deploy → Manage deployments → Edit → New version).
3. ارفع ملفات الواجهة الخمسة على GitHub Pages. ضع رابط الـ Web App في `config.js`.
4. من لوحة الإدارة: أنشئ المخازن، ثم حدّد لكل مستخدم صلاحيته في كل مديول.
5. أدخل الأرصدة الحالية بـ "رصيد افتتاحي" (مدير المخازن) قبل بدء الاستلام والصرف.

## الصلاحيات
- **المشتريات:** طالب شراء / معتمد / مشتريات / مالية / مدير.
- **المخازن:** طالب صرف / أمين مخزن / مدير مخازن / مراجع (اطلاع فقط) / مدير النظام.
- أمين المخزن والمراجع مقيَّدان بمخازن محددة؛ مدير المخازن والإدارة يرون الكل.
- التكلفة والقيم تظهر فقط للمدير ومدير المخازن والمراجع.
- لا أحد يعتمد طلبه بنفسه (طلب شراء / طلب صرف / جرد) إلا مدير النظام.
- الصلاحيات تُفرض في الخادم (Apps Script) وليس في الواجهة فقط.

## الربط بين المديولين
- بند طلب الشراء وأمر التوريد يمكن ربطه بصنف من دليل الأصناف (اختياري).
- أمر التوريد المعتمد يظهر لأمين المخزن للاستلام (جزئي أو كلي، بحد سماح اختياري في الإعدادات).
- الاستلام يزيد المخزون بالتكلفة الفعلية من سعر أمر التوريد (متوسط مرجّح)، ويحدّث نسبة الاستلام وحالة الأمر ("مستلم جزئيًا" ثم "مستلم").
- مع تفعيل الربط لا يمكن تأكيد الاستلام يدويًا؛ للخدمات أو لإقفال أمر ناقص يوجد زر "إغلاق الاستلام" (بسبب إلزامي).
- الرصيد لا يُخزَّن: يُحسب من دفتر حركات لا يُعدَّل، والتصحيح بحركة عكسية فقط.
- زر "فحص سلامة الأرصدة" يطابق الدفتر مع المستندات وأوامر التوريد وطلبات الصرف.

## دورة المخازن
استلام من أمر توريد ← طلب صرف ← اعتماد ← إذن صرف (جزئي ممكن) ← تحويل بين المخازن (مسودة/مرسل/مستلم) ← جرد (إعداد/تقديم/اعتماد) ← عكس الاستلام أو الصرف (مدير فقط وبسبب).

## ما لا يغطيه النظام (بصراحة)
هو نظام داخلي جيد، وليس بديلًا كاملًا لـ ERP تجاري. غير موجود: مرتجع للمورد، مطابقة فاتورة المورد (3-way match)، ميزانيات وبنود موازنة، مرفقات، عملات متعددة، دفعات وتواريخ صلاحية وأرقام تسلسلية، تقييم FIFO (المتوسط المرجّح فقط)، قيود محاسبية، وإعادة ترتيب الحركات عند الاستلام بتاريخ سابق. الأداء مناسب لعشرات الآلاف من الحركات؛ بعدها يلزم قاعدة بيانات حقيقية.

## مديول الحسابات (قيد مزدوج)
**التفعيل:** من مديول الحسابات (مدير النظام) زر "تفعيل الربط المحاسبي". لا يمكن التراجع عنه. يُنشئ دليل حسابات جاهزًا، ويرحّل قيدًا افتتاحيًا بقيمة المخزون الحالية وما استُلم ولم يُسدَّد من أوامر التوريد. يصبح اليوم هو بداية التطبيق المحاسبي، ولا يُقبل مستند أو قيد بتاريخ قبله.

**الصلاحيات (صلاحية الحسابات لكل مستخدم):**
- محاسب: يعدّ القيود اليدوية وسندات القبض والصرف كمسودات، ويسجّل سداد الموردين، ويقرأ التقارير.
- مدير حسابات: يرحّل القيود أو يرفضها (غير قيوده)، ويعكس القيود والدفعات، ويدير الدليل والمشروعات، ويقفل الفترات.
- مراجع: اطلاع فقط.
- مدير النظام: كل شيء، وحده يعيد فتح الفترات المقفلة.
- مستخدم المشتريات بصلاحية "مالية" يسدّد الموردين من أمر التوريد دون دخول مديول الحسابات.

**الربط التلقائي:**
| الحدث | القيد |
|---|---|
| استلام مخزني | مدين مخزون (أو مصروف خدمات) + ضريبة مدخلات، دائن موردون (حسب المشروع) |
| صرف مخزني | مدين مواد مصروفة (حسب المشروع)، دائن مخزون |
| جرد معتمد | صافي العجز أو الفائض مقابل فروقات الجرد |
| رصيد افتتاحي مخزني | مدين مخزون، دائن رصيد افتتاحي |
| سداد مورد | مدين موردون، دائن خزينة/بنك (لا يتجاوز المستحق ولا رصيد النقدية) |
| عكس استلام/صرف/دفعة | قيد عكسي تلقائي |
حالة أمر التوريد تتحول إلى "مدفوع" تلقائيًا عند سداد كامل المستحق، ولا يمكن تغييرها يدويًا بعد التفعيل.

**المشروعات والممولون:** تُعرَّف في الدليل، وتُوزَّع القيود عليها بمطابقة اسم المشروع المكتوب في طلب الشراء/أمر التوريد/طلب الصرف. بدون تطابق يظهر "غير موزع".

**التقارير:** ميزان المراجعة، دفتر الأستاذ، قائمة الإيرادات والمصروفات بأعمدة المشروعات (والممول)، المركز المالي، تقادم الموردين، وفحص سلامة الدفاتر الذي يطابق المخزون والموردين مع المخازن والمشتريات.

**ضوابط:** القيد متوازن دائمًا، دفتر القيود لا يُعدَّل (التصحيح بقيد عكسي)، حسابا المخزون والموردين لا يُرحَّل عليهما يدويًا، وفصل المهام (المُعِدّ ليس المرحِّل)، وإقفال الفترات يمنع كل ترحيل بتاريخ ضمنها.

**حدود مديول الحسابات (بصراحة):** لا ضريبة مبيعات ولا مدخلات غير ضريبة الاستلام، لا أصول ثابتة وإهلاك، لا كشوف رواتب، لا تسوية بنكية، لا ميزانية تقديرية، لا عملات متعددة، لا دفعات مقدمة للموردين، ولا مطابقة فاتورة المورد. لا قيود إقفال سنوية (الفائض يُحسب في المركز المالي). تقارير الدفتر تقرأ كل الحركات، والأداء يناسب عشرات الآلاف من الأسطر.

## التصدير إلى Excel (export.js)
- زر **تصدير Excel** في الشريط العلوي يصدّر الشاشة الحالية (كل جداولها وبطاقات الملخص) كما هي معروضة، بما فيها الفلاتر والبحث المطبّق، دون عمود الإجراءات. التقارير (ميزان المراجعة، دفتر الأستاذ، قائمة الدخل، المركز المالي، أعمار الديون) تُصدَّر بعد تشغيلها.
- زر **Excel** بجوار الطباعة في أمر التوريد وإذون الاستلام/الصرف/التحويل والقيود.
- الإعدادات ← **تصدير كل البيانات** (للمدير): 17 ورقة (طلبات، أوامر، بنود، موردون، أصناف، مخازن، مستندات، دفتر المخزون، دليل الحسابات، مشروعات، قيود، سطور، دفعات، مستخدمون بدون كلمات مرور، سجل العمليات).
- الأرقام تُصدَّر أرقامًا حقيقية؛ الأكواد والهواتف والأرقام الضريبية تبقى نصًا؛ النصوص التي تبدأ بـ = تبقى نصًا (لا تُنفَّذ كمعادلات). الورقة من اليمين لليسار مع تجميد الرأس وفلتر.
- حدود: التصدير من الشاشة يشمل البيانات المحمّلة فقط (مثلًا آخر 300 قيد)؛ للكل استخدم «تصدير كل البيانات».
- الطلبات المتكررة (ضغط مزدوج) لا تُنفَّذ مرتين: كل نافذة تحمل معرّف طلب يتجاهله الخادم إن تكرر.

## السرعة والمزامنة الفورية
- كل عملية حفظ/اعتماد تُرسل **طلبًا واحدًا** للخادم يعيد النتيجة مع أحدث البيانات (كان طلبين: تنفيذ ثم إعادة تحميل)، وقراءة كل شيت تتم مرة واحدة في الطلب الواحد.
- المزامنة بين المستخدمين: كل شاشة تفحص رقم نسخة البيانات (`ping` خفيف بلا قراءة شيتات) كل 3 ثوانٍ أثناء النشاط، فإذا عدّل مستخدم آخر شيئًا تتحدث شاشتك تلقائيًا. لا تتحدث أثناء كتابتك في نافذة أو حقل (تُحدَّث فور انتهائك)، ويُحفظ نص البحث ومكان التمرير.
- توفير الحصة: يتباطأ الفحص إلى 15 ثانية بعد دقيقتين خمول وإلى 60 ثانية بعد 10 دقائق، ويتوقف والتبويب مخفي. حصة Apps Script اليومية (حساب Gmail العادي نحو 90 دقيقة تنفيذ) قد تُستهلك مع عدد كبير من المستخدمين المفتوحين طوال اليوم؛ الأفضل حساب Google Workspace عند التوسع.
- حدود صريحة: Apps Script نفسه يستغرق عادةً من نحو ثانية إلى ثلاث للعملية الواحدة (بدء تشغيل وقراءة الشيتات) ولا يمكن جعله لحظيًا كقاعدة بيانات حقيقية؛ المزامنة شبه فورية (ثوانٍ) لا لحظية. لتحسين أكبر لاحقًا يلزم نقل الخادم إلى قاعدة بيانات فعلية.
- العرض: الواجهة تملأ عرض الشاشة كاملًا.

## صلاحيات التابات (تقييد دقيق لكل مستخدم)
- من الإدارة ← المستخدمون ← تعديل: قسم «صلاحيات التابات» يعرض كل تابات المشتريات والمخازن والحسابات (22 تابًا). لكل تاب ثلاث حالات: **كامل** (حسب دور المستخدم) / **عرض فقط** (يرى ولا يعدّل: تُزال أزرار الإضافة والتعديل والاعتماد، وتبقى الطباعة والتصدير والتقارير) / **مخفي** (يختفي التاب).
- **إقفال مديول كامل:** اختر «بدون وصول» في صلاحية المديول، أو أخفِ كل تاباته فيختفي المديول.
- الفرض يتم في **الخادم** وليس الواجهة فقط: كل إجراء مرتبط بتابه (مثلًا حفظ مورد ← تاب الموردون، الاستلام ← تاب الاستلام، عكس مستند حسب نوعه)، ويُرفض مع رسالة واضحة لو كان التاب مخفيًا أو للعرض فقط. التقارير (ميزان المراجعة، دفتر الأستاذ، القوائم) تُمنع إن كان تابها مخفيًا.
- البيانات المرتبطة بتاب مخفي لا تُرسل للمتصفح (مثل مستندات الاستلام، القيود، الدفعات)، بشرط ألا تكون ظاهرة في تاب آخر مفتوح له؛ مثلًا الموردون يبقون ظاهرين لمن يرى أوامر التوريد لأنها تعرض أسماءهم.
- التغيير يسري فورًا على المستخدم المتصل (عبر المزامنة) دون إعادة دخول، ويُسجَّل في السجل. المدير العام غير خاضع للتقييد.
- يلزم تشغيل `setup()` مرة بعد الترقية (يضيف عمود `tabs` لشيت المستخدمين).
- حدود صريحة: التقييد على مستوى التاب لا الحقل أو السجل (لا «مشروع معيّن» أو «مبلغ أقصى»). لوحات التحكم تعرض ملخصات من بيانات تابات أخرى، فأخفِ لوحة التحكم أيضًا إن أردت منع الأرقام الإجمالية.

## دليل المشاريع (تكويد مركزي)
- من الإدارة ← تاب **المشاريع**: لكل مشروع كود ثابت (تلقائي PRJ-001 أو كود تحدده مثل GH-01) واسم وممول وتاريخ بداية ونهاية وملاحظات وحالة (نشط/موقوف).
- المشروع يظهر **كقائمة منسدلة «كود · اسم»** في طلب الشراء وأمر التوريد وطلب الصرف والصرف المباشر، ويُحفظ **كوده** في المستند، وتُوزَّع عليه القيود المحاسبية تلقائيًا (تُحوَّل الأسماء القديمة للكود عند الحفظ). المستخدم لا يستطيع كتابة مشروع غير موجود في الدليل، والموقوف لا يُختار في مستندات جديدة وتبقى مستنداته القديمة.
- **إلزام اختيار مشروع** (إعداد اختياري) في نفس التاب.
- القفل: لا يتغير كود المشروع بعد استخدامه في مستند أو قيد؛ والاسم يمكن تعديله (المستندات تحمل الكود) إلا إن وُجدت مستندات قديمة مرتبطة به بالاسم.
- المستندات القديمة المكتوب فيها اسم مشروع نصًا تظهر في قائمة «مشاريع مكتوبة يدويًا قبل التكويد» مع زر لإنشاء مشروع بنفس الاسم فتُربط تلقائيًا.
- قبل تعريف أي مشروع يبقى الحقل نصًا حرًا كما كان. مدير الحسابات (بعد تفعيل الحسابات) يستطيع أيضًا إدارة المشاريع من تاب «المشروعات والممولون».
- يلزم تشغيل `setup()` بعد الترقية (يضيف أعمدة التواريخ والملاحظات). تصدير كل البيانات يتضمن المشاريع وعمود اسم المشروع.

## البحث داخل القوائم المنسدلة
أي قائمة منسدلة فيها أكثر من 6 خيارات (الموردون، الأصناف، المشاريع، الحسابات...) تعمل كحقل بحث: اكتب جزءًا من الكلمة (من أي موضع) فتُصفّى الخيارات فورًا، مع تجاهل التشكيل والهمزات (أ/إ/ا) والتاء المربوطة (ة/ه) والياء (ى/ي). تعمل بالأسهم وEnter وEsc والفأرة. القوائم القصيرة تبقى عادية.

## مديول التبرعات (جديد)
**الملفات:** `Donations.gs` (الخادم) و `mod-donations.js` (الواجهة). بعد لصق الملف شغّل `setup()` مرة (ينشئ شيتات المتبرعين والحملات والتبرعات والالتزامات وسجل التواصل، ويضيف عمود `don` للمستخدمين).

**التابات (8، كل واحد يُمنح أو يُخفى أو يُقيَّد «عرض فقط» لكل مستخدم):** لوحة التحكم، المتبرعون، التبرعات، الالتزامات، التواصل والمتابعة، الحملات والمبادرات، قنوات التحصيل، التقارير. وفي مديول الحسابات تاب «تحصيل التبرعات».

**الصلاحيات:** مسؤول تبرعات (يسجّل مسودات ومتبرعين وتواصل والتزامات، ويعدّل ما أنشأه فقط)، مدير تبرعات (يعتمد ويلغي ويدير الحملات ويشطب الالتزامات ويحذف المتبرع غير المستخدم)، مراجع (اطلاع فقط). مدير النظام يملك كل شيء.

**الدورة:**
- **المتبرعون:** فرد / شركة / جمعية أو مؤسسة / جهة حكومية / جهة دولية أو ممول / أخرى؛ كود تلقائي DNR-0001؛ منع تكرار الهاتف، وتنبيه عند تشابه الاسم (يتجاهل الهمزات والتشكيل)؛ علامة «لا يرغب في التواصل»؛ كشف حساب لكل متبرع (طباعة وExcel).
- **المتبرع السريع:** زر «+ متبرع جديد» داخل نموذج التبرع يفتح نموذجًا مصغرًا (الاسم والنوع والهاتف) مع نفس فحص التكرار، ثم يعود للتبرع وهو مختار.
- **التبرع:** نقدي (نقدي، تحويل، شيك، بطاقة، محفظة) أو عيني (أصناف بقيمة تقديرية تدخل مخزنًا). يُسجَّل مسودة ثم **يعتمده مدير آخر** (فصل المهام؛ مدير النظام مستثنى) فيصدر **إيصال RCP-سنة-001** بالتفقيط. لا يُعدَّل بعد الاعتماد؛ يُلغى بسبب ويُعكس أثره.
- **الربط بالمشاريع:** التبرع والحملة والالتزام يختارون مشروعًا من دليل المشاريع؛ التبرع «المقيَّد» يلزمه مشروع؛ تقرير «تمويل المشاريع» يقابل التبرعات بالمصروفات المرحّلة على المشروع.
- **قنوات التحصيل:** (إنستاباي، البنك الأهلي، بنك مصر، أونلاين، الخزينة...). لكل قناة وسيلة دفع وحساب خزينة/بنك من دليل الحسابات واشتراط مرجع العملية. بعد تعريف قناة نشطة يصبح اختيارها إلزاميًا في التبرع النقدي. يُنشئها مدير التبرعات.
- **الربط بالحسابات (إن فُعّلت) — بخطوتين:** (1) مدير التبرعات يعتمد التبرع ويصدر الإيصال فيصبح «بانتظار تأكيد الحسابات» دون قيد. (2) محاسب أو مدير حسابات يفتح تاب «تحصيل التبرعات» في مديول الحسابات، يتأكد من وصول المبلغ، ويؤكد (الحساب مقترح من القناة وتاريخ التحصيل الفعلي) فيُرحَّل القيد: مدين الخزينة/البنك، دائن إيراد التبرعات المقيدة 4110 أو العامة 4120 موزعًا على المشروع. لا يحتاج مستخدم الحسابات لصلاحية على بيانات المتبرعين. إلغاء تبرع بانتظار التأكيد لا يحتاج عكس قيد، وإلغاء المؤكد يعكس القيد. الفترة المقفلة تمنع التأكيد والإلغاء. `acctCheck` يفحص مطابقة القيود للتبرعات. التبرع النقدي غير المؤكد لا يظهر في الدفاتر (ويظهر عدده ومبلغه في لوحة التبرعات).
- **الربط بالمخازن:** التبرع العيني عند الاعتماد ينشئ مستند «استلام تبرع عيني» (DNI) يزيد رصيد الصنف بالقيمة التقديرية، وقيده: مدين المخزون، دائن 4130 (تبرعات عينية). لا يُلغى التبرع إذا تحرك الصنف بعده (يُمنع حتى لا يختل الرصيد).
- **الالتزامات (وعود التبرع):** تُربط بتبرعات فعلية وتتحول تلقائيًا إلى «مُحصَّل» عند اكتمال التحصيل؛ تظهر المتأخرة في لوحة التحكم وتقرير التقادم.
- **التواصل:** سجل اتصال/زيارة/واتساب... بنتيجة وموضوع وموعد متابعة؛ المتابعات المستحقة في لوحة التحكم.
- **التقارير:** حسب الحملة (مع المستهدف والنسبة)، النوع، الوسيلة، الشهر، عام/مقيد، أكبر المتبرعين، المنقطعون، تقادم الالتزامات، تمويل المشاريع. كلها قابلة للطباعة والتصدير إلى Excel. تصدير «كل البيانات» يضم 5 أوراق للتبرعات.

**حدود (بصراحة):**
- الالتزامات لا تُقيَّد محاسبيًا (مذكرة فقط)؛ الإيراد يُقيَّد عند التحصيل الفعلي.
- التبرع العيني بقيمة تقديرية يحددها المستخدم، والعملة جنيه مصري فقط.
- التبرع العيني يُرحَّل قيده فورًا عند اعتماد مدير التبرعات (لأن المخزون يدخل فورًا ولا تتطابق الدفاتر مع المخزون بدونه)، ولا يمر بتأكيد الحسابات.
- لا يوجد التزام متكرر (اشتراك شهري) تلقائي، ولا إرسال رسائل بريد/واتساب من النظام (السجل للتوثيق فقط).
- لا يوجد بوابة دفع إلكتروني ولا إقرار ضريبي/خصم؛ الإيصال داخلي وليس مستندًا ضريبيًا رسميًا.
- بيانات المتبرعين حساسة: امنح صلاحية التبرعات لمن يحتاجها فقط، واستخدم «عرض فقط» للتابات التي لا تلزم.
- التبرع يُسجَّل بتاريخ اليوم أو أقدم (لا تواريخ مستقبلية). حصة Apps Script اليومية تنطبق كما في باقي المديولات.

## سرعة التنفيذ والتزامن الفوري (محدّث)
**أسباب البطء:** كل عملية كانت تعيد قراءة كل شيتات النظام (≈20 قراءة) لتُرجع الشاشة محدّثة. الآن:
- **ذاكرة قراءة مضغوطة بين الطلبات (CacheService):** لكل شيت نسخة مخزنة لها رقم إصدار؛ الكتابة ترفع إصدار الشيتات التي تغيّرت فقط، فتُقرأ الباقية من الذاكرة. في الاختبار: تحميل البيانات من 17 قراءة شيت إلى 1، وعملية الحفظ مع ردّ البيانات المحدّثة من 19 إلى 3.
- فحوصات السلامة (`reconcile` و`acctCheck`) والتصدير الكامل تقرأ **مباشرة من الشيت** دائمًا لكشف أي تلاعب.
- **تعديل الشيت يدويًا:** لا يرفع الإصدار، فيظهر في النظام خلال 10 دقائق، أو فورًا بتشغيل `refreshCache()` من محرر Apps Script. الأفضل التعديل من النظام نفسه.
- **ما لا يمكن تجاوزه:** زمن تشغيل Apps Script نفسه (غالبًا 0.5–2 ثانية للطلب الواحد حتى لو كان خفيفًا) ويتأثر بحمل جوجل. التحسينات تقلل الجزء المتعلق بقراءة الشيتات فقط.

### تزامن فوري بين كل المستخدمين في أي مكان (اختياري: Firebase مجاني)
Apps Script لا يستطيع «دفع» إشعار للمتصفحات، فبدون خدمة خارجية لا يتجاوز التزامن الفحص الدوري (كل ~3 ثوانٍ أثناء النشاط). لتحديث فوري (≈1 ثانية) فعّل قناة إشعار Firebase Realtime Database (الخطة المجانية Spark تكفي؛ لا تُخزَّن بياناتك فيها، فقط علامة تغيير):
1. console.firebase.google.com ← **Add project** (اسم مثل `ghaith-erp`، يمكنك تعطيل Analytics).
2. من القائمة **Build ← Realtime Database ← Create Database**، اختر موقعًا قريبًا، واختر **Start in locked mode**.
3. تبويب **Rules** والصق ثم **Publish**:
```
{
  "rules": {
    ".read": false,
    ".write": false,
    "v": {
      ".read": true,
      ".write": true,
      ".validate": "newData.isString() && newData.val().length < 40"
    }
  }
}
```
4. انسخ رابط القاعدة من تبويب **Data** (مثل `https://ghaith-erp-default-rtdb.firebaseio.com`) بدون شرطة في النهاية.
5. ضعه في `config.js` على GitHub: `FB: 'https://ghaith-erp-default-rtdb.firebaseio.com'` ثم Commit.
6. افتح النظام من جهازين وجرّب: إضافة سجل في الأول يظهر في الثاني خلال ثانية تقريبًا.

**كيف يعمل:** عند نجاح أي كتابة يرسل متصفح الكاتب علامة عشوائية إلى المسار `v` (بدون تأخير على المستخدم)، والمتصفحات الأخرى تستمع للمسار فتفحص `ping` ثم تحمّل أحدث البيانات. عند انقطاع القناة يعود الفحص الدوري ويلتقط التغييرات. **الأمان:** المسار `v` عام القراءة والكتابة لكنه لا يحمل بيانات، ولو عبث أحد به فأسوأ نتيجة طلبات `ping` خفيفة إضافية (تحتاج جلسة صحيحة)، ولا يصل لأي بيانات. بقية القاعدة مغلقة.
**حدود:** لم أستطع تجربتها مع Firebase الحقيقي من بيئتي، اختُبرت مع خادم محاكٍ بنفس البروتوكول (PUT + EventSource)، فجرّبها بعد الإعداد. ويبقى اختيار ما إذا كانت الخطة المجانية تناسب حجم استخدامك (حدود الاتصالات المتزامنة 100).


## دليل الإدارات (تكويد الإدارات)
- من **الإدارة ← الإدارات** (مدير النظام فقط): كود (DEP-001 تلقائي أو كودك) + اسم + مسؤول. الإدارة الموقوفة لا تظهر للاختيار وتبقى مستنداتها.
- تظهر الإدارة في: **بيانات المستخدم** (قائمة اختيار + عمود في جدول المستخدمين)، **طلب الشراء**، **طلب الصرف** (تُختار تلقائيًا إدارة المستخدم في الطلبات الجديدة)، وتُحفظ كوداً في المستند وتُعرض اسماً في القوائم والطباعة، وفي تصدير Excel (ورقة «الإدارات» وعمود «اسم الإدارة»).
- قبل إنشاء أي إدارة تبقى الخانة نصًا حرًا كما كانت. بعد إنشاء الدليل تصبح الإدارة إلزامية وصحيحة في الطلبات الجديدة. الأسماء المكتوبة يدويًا في طلبات قديمة تظهر في «جهات مكتوبة يدويًا» وبزر واحد تُنشأ لها إدارة بنفس الاسم فتُربط.
- كود الإدارة وتغيير اسمها مقفلان بعد الاستخدام.
- **حد صريح:** الإدارة هنا تنظيمية (للمستخدمين والطلبات والتقارير) وليست بُعدًا محاسبيًا في القيود؛ البعد المحاسبي هو المشروع. وصلاحيات الدخول لا تُبنى على الإدارة (تبقى بالأدوار والتابات).

## ربط الحسابات (Account Determination)
- من **الحسابات ← ربط الحسابات** (مدير حسابات أو مدير النظام): كل دور في النظام يشير إلى حساب واحد من دليل الحسابات: المخزون، الموردون، ضريبة المدخلات، مصروف الصرف، مصروف الخدمات، فروقات الجرد، الرصيد الافتتاحي، وإيرادات التبرعات (مقيد / عام / عيني).
- شروط: نوع الحساب يطابق الدور، فعّال، ليس خزينة/بنك، ولا يؤدي إلا دورًا واحدًا. التغيير يسري على القيود **الجديدة** فقط.
- **المخزون والموردون** لا يُنقلان بعد وجود قيود على الحساب الحالي أو الجديد (لأنهما مرتبطان بتسوية الأرصدة مع المخازن والمشتريات).
- حسابات التحصيل النقدية (خزينة/بنك) تُربط بقنوات التحصيل في مديول التبرعات، وليس من هذه الشاشة.
- الدور غير المربوط للتبرعات يُنشأ/يُربط تلقائيًا بالكود المعتاد (4110/4120/4130) عند أول استخدام.

## تسمية النظام
تغيّر الاسم إلى «نظام غيث المتكامل» في عنوان الصفحة وشاشة الدخول؛ «المشتريات» بقيت اسمًا لمديول المشتريات فقط. اسم المؤسسة الظاهر من الإعدادات.

## الأدوار والصلاحيات التفصيلية (الإدارة ← الأدوار والصلاحيات)
**مهم عند الترقية:** شغّل `setup()` ثانية (يُنشئ شيت الأدوار وأدوارًا جاهزة). المستخدمون القدامى (غير مدير النظام) **لا يملكون أي وصول حتى يُسنَد لهم دور** — إما بإسناد دور لكل مستخدم من «المستخدمون»، أو بزر «إنشاء أدوار مطابقة وإسنادها تلقائيًا» الذي يظهر أعلى صفحة المستخدمين فيحوّل صلاحياتهم القديمة (وقيود التابات والمخازن) إلى أدوار مطابقة بنقرة واحدة.

الدور (Role/Profile) يُسنَد لأي عدد من المستخدمين، وتعديله يسري عليهم فورًا، ويتكوّن من:
1. **صلاحية كل مديول** (الدور الأساسي: طالب/معتمد/مشتريات/مالية، أمين/مدير مخازن، محاسب/مدير حسابات، مسؤول/مدير تبرعات، اطلاع).
2. **مصفوفة التابات × الأفعال:** لكل تاب خمسة مفاتيح: عرض (إلغاؤه يخفي التاب وبياناته)، إنشاء/تعديل، اعتماد/ترحيل/تنفيذ، حذف/إلغاء/عكس، تقارير وكشوف. يُفرض في الخادم؛ والفعالية الفعلية = الأضيق بين صلاحية المديول والمصفوفة.
3. **حدود مالية للاعتماد:** اعتماد طلب الشراء، اعتماد أمر التوريد، سداد الموردين، ترحيل القيد، اعتماد التبرع. القيمة الأكبر تُرفض ويلزم مستوى أعلى (الرفض نفسه غير مقيّد بالحد).
4. **نطاق البيانات:** إدارته فقط (إدارة المستخدم)، إدارات محددة، مشروعات محددة، مخازن. يخفي طلبات الشراء وأوامر التوريد وطلبات الصرف ومستندات المخازن والتبرعات والالتزامات والحملات خارج النطاق، ويمنع تنفيذ إجراءات عليها أو إنشاء سجلات بإدارة/مشروع خارجه. سجلات المستخدم نفسه تظهر له دائمًا.
- **نطاق خاص بالمستخدم** (اختياري) يحل محل نطاق الدور (مثلًا أمين مخزن لمخزن بعينه بنفس الدور).
- مدير النظام (admin) فوق كل ذلك. لا يمكن حذف دور مُسنَد لمستخدمين (أوقفه بدل الحذف).

**حدود صريحة:** نطاق الإدارة/المشروع لا يشمل دفتر الأستاذ وميزان المراجعة والقيود (تبقى بحسب صلاحية الحسابات)، وأرقام لوحات التبرعات المجمّعة قد تتضمن سجلات خارج النطاق. زر الطباعة في المتصفح لا يمكن منعه خادميًا؛ صلاحية «تقارير» تمنع جلب بيانات التقارير والكشوف نفسها.

## المرفقات والإشعارات والموازنات (Extras.gs / mod-extras.js)
- **المرفقات:** 📎 داخل نماذج طلب الشراء وأمر التوريد وطلب الصرف والمستندات المخزنية والقيد والتبرع والعهد/الأصول. تُحفظ على Google Drive لمالك السكربت (مجلد «غيث ERP - المرفقات») ولا تُعطى روابط مباشرة؛ التنزيل عبر النظام فتُفرض الصلاحيات. حد 2.5 ميجابايت للملف و20 ملفًا للسجل، وصيغ محددة (pdf، صور، office، txt، csv).
- **الإشعارات:** جرس في الأعلى: طلب بانتظار الاعتماد، قرار على طلبك، قيد بانتظار الترحيل، تبرع بانتظار تأكيد الحسابات… ويمكن للمدير تفعيل إرسالها أيضًا بالبريد (الإعدادات ← الإشعارات، ويتطلب بريدًا في بيانات المستخدم). حدود Apps Script اليومية للبريد سارية.
- **الموازنات (الحسابات ← الموازنات):** موازنة لكل مشروع (إجمالية أو لكل حساب مصروف) بفترة. تقرير الموازنة مقابل الفعلي والارتباطات (أوامر توريد معتمدة غير مستلمة). الرقابة عند اعتماد أمر التوريد: بدون / تنبيه / منع. الفعلي من القيود المرحّلة على المشروع.

## الخزينة والأصول الثابتة (Treasury.gs / mod-finance2.js) — تابات جديدة داخل الحسابات
يلزم تفعيل الربط المحاسبي. كل تاب له صلاحياته في مصفوفة الأدوار.
- **التحويلات:** بين خزينة وبنك (قيد فوري، لا يؤثر على الإيراد/المصروف) مع منع السحب بما يتجاوز الرصيد، والإلغاء بقيد عكسي بسبب.
- **الشيكات:** سجل متابعة للصادر والوارد بحالاته وتنبيه الاستحقاق ومنع تكرار رقم الشيك. **لا تنشئ قيودًا تلقائية** (الصرف/التحصيل الفعلي يُسجَّل بالسداد أو القيود).
- **التسوية البنكية:** استيراد كشف الحساب (لصق/CSV: تاريخ،بيان،مبلغ،مرجع)، مطابقة تلقائية (نفس المبلغ ±3 أيام) ويدوية، وتقرير يُظهر الفرق غير المفسَّر مقابل رصيد الكشف. القيود المعكوسة مع عكسها تُستبعد من المطابقة.
- **العهد والسلف:** مسودة ← صرف (مدين «عهد وسلف العاملين» 1410) ← تسوية جزئية/كاملة (مصروفات على المشروع + مردود نقدي) مع عكس آخر تسوية وإلغاء العهدة غير المسوّاة.
- **الأصول الثابتة:** سجل بالتكلفة والتخريدية والعمر بالأشهر والموقع والأمين والمشروع؛ اقتناء نقدي بقيد أو أصل قائم (مع مجمع إهلاك افتتاحي للأصول قبل بداية التطبيق، ويُرحَّل رصيده الافتتاحي بقيد يدوي)؛ **إهلاك شهري بالقسط الثابت** بقيد واحد، لا يتكرر لنفس الأصل والشهر، ويُعكس من الأحدث؛ **استبعاد/بيع** بقيد يحسب الربح/الخسارة. حسابات 1410/1510/1590/5310/4190/5290 تُنشأ تلقائيًا وتظهر في «ربط الحسابات».
- **حدود صريحة:** طريقة إهلاك واحدة (قسط ثابت)، لا إعادة تقييم/اضمحلال، لا تقسيط لعملية الاقتناء عبر المشتريات (تُسجَّل الأصول يدويًا)، والتسوية البنكية لا تُنشئ قيودًا للرسوم تلقائيًا (تُسجَّل بقيد يدوي ثم تُطابَق).
